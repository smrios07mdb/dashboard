## Deviations

**D-1 — CORS preflight headers are unreadable from the isolated world.** The `OPTIONS`
returned 204 but `Access-Control-*` response headers came back empty: they are not
exposed to script, and `Origin` is a forbidden header the fetch cannot set. Cost: §0.2
is recorded as a status code plus indirect proof (every cross-origin GET/POST/PATCH/
DELETE in the run succeeded from the production origin), not as the header assertion the
spec words. A spec fix would state that form.

**D-2 — one placement POST produced two VEVENTs.** Full evidence above. Cost: one extra
proxy `DELETE` to remove the orphan before B2b, and ~4 minutes. Not attributed; not
chunk 47's code. Worth a spec line telling runners to check `plannerEvents` for exactly
one uid after B2 and to clear extras before the move, since an unclaimed planner event
otherwise draws an orphan-sweep delete into the B2b window.

**D-3 — HTTP methods *are* observable on prod, contradicting the spec's premise.** The
spec's run rules say the prod harness gets "URL, `responseStatus`, completion order —
**no HTTP method**", and tell runners to bracket windows and corroborate via DB state.
Chrome MCP's `read_network_requests` returns `method` and `statusCode` per request from
outside the page, so the CSP does not restrict it. This run used it for B2b attempts
2–3, B3b and B4, and it is what let B4 be scored exactly rather than inferred. Two
operating notes: tracking starts only when the tool is first called, and it resets on
reload — arm it after every reload, before the window you care about. This should be
added to the spec's harness rules and to `CLAUDE.md`; it removes most of the awkwardness
the prod CSP imposed.

**D-4 — B2b measures three PATCHes per drag-move, reproducibly, and the assertion as
worded cannot separate that from the regression it targets.** 3/3/3 across three
attempts, including one with no proxy error at all. The app provably issues one (single
call site, single DB write, no retry layer, no failure toast on the 502), and the
reconcile — the thing chunk 47 changed — issued zero. Two consequences:

1. The chunk-47 change is not falsified by this; if anything B3b and B4 confirm it.
2. The B2 count assertion counts *network requests* where it means *app-issued
   mutations*, and prod has at least one layer beneath the app that can multiply a
   request. Even with the interposed `/busy` refresh the check now fails for a reason
   unrelated to its subject — which is the same class of defect the amendment was
   written to fix, one level down.

   What would settle the attribution, none of it in this run's scope: reproduce a move
   from a real mouse drag rather than synthesized pointer events; or with the service
   worker unregistered; or read the three request bodies (a page-world hook the prod CSP
   blocks — a local `npm run dev` run against the same proxy would do it in minutes).
   Recommend the local reproduction first: it separates "the app sends three" from
   "something below it sends three" without touching prod.

**D-5 — the spec's prod instrument over-counts.** `PerformanceObserver` on resource
entries reported 2 for B4's window where DevTools reported 1 actual `DELETE`, and the
two instruments agreed elsewhere (B2b attempt 3: 3 and 3; B3b: 1 and 1). A fetch served
through a service worker can surface more than one resource-timing entry. Any assertion
phrased as an exact count should be read off the DevTools log (D-3), with the
`PerformanceObserver` kept for ordering and for windows marked during a run.

**D-6 — console-error cleanliness could not be asserted retroactively.** Chrome MCP's
console tracking, like its network tracking, starts at first call; it was armed only at
cleanup, and returned nothing. The spec's substitute (`window.onerror` /
`unhandledrejection`) was installed but lives in the isolated world and cannot see
page-world exceptions. What can be asserted positively: zero failure toasts, zero
isolated-world errors, and every request in the run returned 200/201/204 except the
single 502 in B2b attempt 2. Future runs should call `read_console_messages` once
immediately after the first load.

**Harness notes (no cost, worth carrying forward).** `javascript_tool` does not await
promises — the documented DOM-sink pattern was used throughout. It also refuses to
return any output that looks like a query string (`[BLOCKED: Cookie/query string data]`),
so netlog URLs must be sanitized to path + parameter *names* before being returned. And
harness-issued `/busy` probes are distinguishable from the app's in the DevTools log by
their unencoded `:` characters.

below the app's JavaScript, is not the drift loop, and is not attributed — reported as

## Orchestrator addendum (chunk 48, added when this record was committed)

This record is preserved verbatim above. One thing in it is wrong and one thing said
about it afterwards was also wrong; both are settled by the re-measure
(`claude/chunk-47-b2b-remeasure-2026-08-31.md`, run `0831h`) and closed in chunk 48.

**The count of 3 was correct.** Both instruments agree at three method-`PATCH`,
status-200 `/api/calendar/events` requests per drag-move, and the netlog — the
non-duplicating one — is among them. Nothing about the measurement needs revisiting.

**Its attribution was not.** "The multiplication sits below the app's JS" (D-4, and the
Bottom line) is false. All three are the app's own code, and the two extras are the
reconcile effect, not the mirror's update path. Two causes, both confirmed against the
committed source at `471a3eb`:

1. **The reconcile runs against optimistic state.** `move` (`Planner.tsx:694–720`)
   patches `blocks` optimistically, *then* awaits `repo.scheduledBlocks.update`, and
   calls `mirror.afterUpdate` only after that resolves (~+631 ms live). The reconcile
   effect has `blocks` in its deps, so it fires on the optimistic frame at +6 ms,
   compares the moved block against a `/busy` snapshot holding the pre-move times, finds
   drift, and "repairs" it — writing the very times the mirror is about to write.
   `creating` guarded this for creates; nothing guarded updates. Closed by **D12**: a
   `pending` set of block ids whose mirror write the caller owns, marked synchronously
   *before* the optimistic patch, which the backfill and drift loops skip.
2. **`blockSignature` compared timestamp strings, not instants.** `toInstant` emits
   `…T20:00:00.000Z`; `scheduledBlockFromRow` passes PostgREST's `…T20:00:00+00:00`
   through verbatim. Same instant, different text — so `patchBlocks(saved)` looked like
   new content and the reconcile ran a second time, the +641 ms PATCH alongside
   `afterUpdate`'s. Not move-specific: **every** block save has re-run the reconcile for
   free since chunk 43. Closed by **D13**: the signature normalizes through `Date.parse`.

This is the fourth manifestation of one root cause — chunk 46's F2 unschedule
double-delete, chunk 47's G2 move double-PATCH, and now these two. The pattern is always
the reconcile acting on state a mutation is mid-way through owning.

**The gate's counter-reading was also wrong.** The reading that the 3 was an instrument
artefact does not survive the re-measure: two independent instruments agree at 3, and no
local dev run was needed to attribute it.

**D-5 is reproduced and real.** In the same `0831h` session, resource timing again
reported **2** entries for the unschedule's single `DELETE` where the netlog reported
**1**. Resource timing stays **disqualified as a counting instrument**; it is for
ordering, for windows marked during a run, and for mount-cost reads. Exact counts come
off the driver's network log, which carries the HTTP method.

**What still stands from this record.** B3b and B4 pass as written and are not revisited.
The post-move reconcile fired zero calendar calls *after* the blocks refetch, which is
what G2 actually asserted — so chunks 46 and 47 stand, and B2b's 3 is a separate defect
that predates both.
