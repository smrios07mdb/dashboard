## Findings for the orchestrator

**F1 — B3b as amended is still not runnable in the fixture sequence the spec prescribes. The check
passed only after inserting a step the spec does not mention. This is a spec defect; chunk 43's
code is correct.**

The amended spec says: "With the current week reconciled and a mirrored block in sync, drift the
block by SQL … the realtime echo from the SQL write itself bumps `dashboardRefreshKey`, so on prod
the drift PATCH should fire within the echo's refetch." Run as written, it fired nothing (attempt 1
above: echo refetch landed, blocks state updated, block re-rendered at the drifted time, zero
`/events` over 90 s, plus a week away-and-back that also produced zero).

The cause is not the dedup. It is that "in sync" is true of the DB and the calendar but **not of
the app's in-memory busy snapshot**, which is what the mirror actually compares against:

```
git show bf3dfa4:src/screens/Planner.tsx
:613    const plannerEvents = busyState.busy?.plannerEvents
:614    if (!plannerEvents) return
:615    void mirror.reconcile({ key: `${weekKey}:${busyRefreshKey}`, blocks, plannerEvents, … })
:624-635  deps include `blocks`  ← the effect DOES re-run when blocks change

git show bf3dfa4:src/lib/plannerCalendarMirror.ts
:146    const signature = blockSignature(blocks)
:147    if (reconciled.get(key) === signature) return      ← chunk 43's content signature, working
:179    const eventByUid = new Map(plannerEvents.map((e) => [e.uid, e]))
:180    for (const b of blocks) {
:181      if (!b.calendarUid) continue
:182      const ev = eventByUid.get(b.calendarUid)
:183      if (!ev) continue                                ← the silent exit
```

`busyState.busy.plannerEvents` is the snapshot from the **last `/busy` fetch**. In the spec's own
B-setup order — mount the week, *then* place the block — that snapshot was taken **before** the
event existed, so it is `[]`. The block carries a `calendarUid`, so backfill skips it (`:167`);
the drift loop then looks the uid up in an empty map and `continue`s at `:183`. The effect ran, the
signature was new, the dedup did its job — there was simply nothing to compare against. And the
snapshot cannot be refreshed without a `/busy` fetch, which needs exactly the `busyRefreshKey`
bump, week change or remount that B3b forbids.

Attempt 2 passed because the intervening reload gave the document a `/busy` snapshot that contained
the event. **Concrete ask: amend B3b to insert one step** — after B2's placement, force a single
`/busy` refresh (a page reload is sufficient and is the cheapest) *before* drifting, so the app's
snapshot contains the mirrored event; then drift and assert on the echo. Without that step the
check is vacuous on any build, in the same structural way chunk 42's original B3 was. Note also
that the reload fallback the spec currently offers is **not a substitute**: it is a remount, which
repaired drift before chunk 43 too, so a run that relies on it cannot tell the fix from its absence.

Product question left open, unchanged from chunk 42's F2(b): between the mirror write and the next
`/busy` refresh, this device cannot detect its own drift. In normal use the window closes on the
next remount or week change, but it exists and is invisible to the user.

**F2 — B4's unschedule issues the delete-by-uid twice.** Two `@proxy/api/calendar/events?uid=hupo-block-0ad53e99-…`
calls, +9 ms and +184 ms after the click, both 200. Consistent with the mutation's own delete plus
the reconcile's orphan sweep (`plannerCalendarMirror.ts:155-162`) firing on the blocks refetch that
follows — blocks becomes `[]`, the in-memory `plannerEvents` still holds the event, so it is
correctly classified an orphan and deleted again. Harmless (delete-by-uid is idempotent; the proxy
returns `missing` rather than erroring) and the end state is right, but it is a wasted round-trip on
every unschedule and it will show up as a spurious second call in any future netlog assertion that
counts `/events` in an unschedule window. Worth either suppressing or documenting in the spec.

**F3 — a stale `hup:todayPlan` entry is discarded on read but left on disk.** After the day-rollover
reload, `localStorage['hup:todayPlan']` still held the verbatim `2026-08-30` string. The discard is
semantically complete — the next manual toggle rewrote it as
`{"date":"2026-08-31","pinned":["24d4f658-…"],"removed":[]}`, dropping yesterday's `removed` entry —
so no behaviour is wrong. But a device that is opened, not touched, and closed keeps yesterday's
deltas on disk indefinitely, and any future check that asserts on the key's *presence* rather than
its effect will read the wrong thing. Cheap to fix (prune on read); at minimum the spec should
assert on the derived membership, as this run did, never on the key's presence.

**F4 — harness note: `Control Chrome` `execute_javascript` requires an IIFE.** A top-level `return`
is a syntax error and returns the bare string `missing value`, which chunk 42's notes attribute to
a thrown exception or a dead connection. Wrap every body as
`(function(){ try { … } catch(e){ return 'ERR:'+e.message; } })()`. Also: the prod toast region is a
`section[aria-live="polite"]` whose injected children carry **no** `role`, `data-sonner-toast` or
`toast` class — a `MutationObserver` predicate that tests the added node for those attributes
(chunk 42's) silently captures nothing on prod. Observe that section directly and take every added
element's `innerText`. Both notes belong in the spec's harness section.

**F5 — the reconcile can be observed cheaply without a mount-time harness.** After any reload,
`performance.getEntriesByType('resource')` still holds the whole mount, so `/busy` and `/events`
counts for a fresh load can be read *after the fact* without racing to install a
`PerformanceObserver` before the app boots. Used for §0.5 and for attempt 1's reload evidence;
worth writing into the harness notes, as it removes the main reason prod runs were awkward to
instrument.
